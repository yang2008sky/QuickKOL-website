# Twitter Algorithm: Read the X Feed Evidence

Status: local review draft; confirm the publication date before release.

Interpret public Twitter/X recommendation evidence and validate what a brand observes by surface.

![Two streams of candidate posts feed a ranking illustration beside a separate observation log.](../public/assets/blog/twitter-algorithm-x-feed-evidence.jpg)

QuickKOL editorial graphic; not actual account metrics or a platform interface.

The Twitter algorithm commonly refers to X’s mechanisms for selecting, ranking or recommending content. State whether you mean For You, Following, search or replies. Help pages explain surfaces, public code describes parts of a particular version and account observations show what was visible at a particular time. Use each for the question it can answer.

## Name the surface first

The [X timeline help](https://help.x.com/en/using-x/x-timeline) distinguishes For You and Following. The former combines material from followed accounts or topics with recommendations. The latter presents posts from accounts you follow. Track replies, notifications, search and promoted placements separately. If a colleague says the algorithm did not show a post, ask whether they checked their own profile, another account’s recommendation feed, search or a reply thread. Record time and surface. Use the [social media operating plan](https://www.quickkol.com/blog/social-media-marketing-operating-plan/#answer) to define the test content, account and task. A brand can study one distribution question without explaining the entire system. A useful example might be whether someone can find an event update from a known profile and whether it contains the correct date. That is different from testing appearance in a personalized feed. Start with the question the team can resolve, then choose the evidence. If the relevant platform surface changes during the project, give the new observation a separate row.

## Read public guidance with its scope intact

The [X Home recommendation disclosure](https://help.x.com/en/resources/recommender-systems/for-you-home-timeline-recommendations) describes finding content from inside and outside a viewer’s network, ranking relevance and applying filtering. It can explain why two viewers may see different sets. It cannot establish that a particular interaction always raises the rank of a post. Record market, observation time, account state, follow relationship and selected tab. Do not infer a penalty, concealment or suppression from an isolated result. A post might simply be outside the portion of the feed someone saw. Another person could encounter it later or through a different entry point. For an operational check, inspect whether the public post is reachable under the expected conditions, then treat feed placement as its own question. If the team needs to assess a notification, review the relevant notification settings and observation scope. Keep the report readable for someone who has not seen the screenshots. State whether the evidence came from public documentation, a native metric or a manual observation.

## Distinguish historical code from newer For You material

The [historical Twitter recommendation repository](https://github.com/twitter/the-algorithm) describes the For You and recommended notification components it published. The [xAI public For You repository](https://github.com/xai-org/x-algorithm) describes candidate sourcing and ranking components such as Thunder and Phoenix. Cite the repository, review date and relevant module. Keep the versions distinct and avoid applying an older architecture or weight to all current products. Public material does not establish the production configuration for an individual request or show that search and paid delivery use the same rules. If a claim depends on code, identify the file or README section and the version you inspected. A copied diagram from an earlier project may still help explain one historical implementation when labeled accordingly. It does not establish what happened to a recent post. The safest use of code in a brand decision is often to clarify which question it does and does not cover. A buyer can then use native reports and a documented observation for the campaign itself. If repository documentation changes, preserve the cited version when making a time-specific claim.

## Design a repeatable observation

Suppose a repair shop publishes an event update and wants to know whether people can find the changed date. Have permitted colleagues check the profile, Following and For You using their normal accounts. Record time, device and the portion of the surface reviewed. Note the actual wording, whether the original or a repost appeared and what someone had to open to find the update. Do not keep refreshing until it appears and call that a guaranteed placement. If one observer follows the account and another does not, record those conditions separately. A missing observation applies only to what was checked. Keep a baseline using a previous comparable update. If the older one was pinned or shared by a partner, record the difference. An observation exercise can uncover a profile navigation problem without revealing why the recommendation system selected a particular post. For a high-priority schedule change, give readers a reliable direct route as part of the content plan and use feed observations as supplementary evidence.

## Keep replies, ads and organic reporting distinct

Finding a reply under a post does not establish that it appears in the same position to another viewer. For available advertising reports, keep asset, campaign, account and time. Public views, reported interactions and website bookings each require their own definitions. Use the [campaign measurement guide](https://www.quickkol.com/blog/creator-campaign-measurement/#answer) to set window and denominator. Suppose a brand posts and advertises during the same event. If the evidence cannot separate them, do not assign the entire change to either one. Verify relevant usage rights separately if a creator’s asset is involved. An organic post may generate useful questions even when ads account for most verified site visits. Keep both findings and give each a source. If a report changes after the first observation, record the new date and definition. A colleague should be able to understand how a native platform value differs from a website event. Do not sum metrics from different surfaces merely because they use a familiar label.

## Use a counterexample to test a delivery assumption

Suppose two colleagues open the recommended feed at the same time. One sees the brand post. The other does not in that review window but can open it directly from the profile. The supported facts are that the post was reachable in the observed conditions and the two experiences differed. The test does not isolate format, engagement weights or account settings as the cause. If the aim is to make a schedule change findable, improve the profile explanation and direct link. If recommendation coverage matters, define a separate observation method. Another test could hold the asset and time constant while observing several accounts with disclosed follow conditions. It still cannot show every user’s experience. Avoid treating a small group as an audience benchmark. If the company needs a paid result, test an authorized campaign with its own budget and reporting. The brand can improve clear communication from evidence it already has, even when ranking questions remain open.

## Maintain evidence versions and public wording

Write that one of two For You observations included the post. Do not convert that into a claim that half of users were prevented from seeing it. If relying on public documentation, include the surface and publication or review date. When correcting a prior claim, retain the original wording, revision, source and date. Separate the changes the team can make from unresolved system hypotheses. Give the next reviewer purpose, method, account conditions and appropriate sharing scope. If a vendor provides a ranking score, ask what it measures and whether it is independently reproducible under the project’s conditions. Compare it with the direct observation without treating the two as interchangeable. A short editorial claim can be accurate if it says exactly which evidence was observed and where. That also makes it easier to update when a repository or help page changes.

## Plan the next round around the user’s task

If the post does not make the date clear, improve the wording and profile route. If readers can see the content but cannot reach the booking page, review the link. If the issue is a missing coverage measure, repeat an appropriate observation or leave the question open. Each step needs a named owner and date. Keep the published link and verified version with the result so someone can repeat the check without guessing which post mattered. A concise test that answers a user’s question is more actionable than a long list of unsupported ranking theories.

## Preserve before and after evidence in two observations

Imagine that a brand revises a notice about a repair visit. In the first observation, two colleagues find the old wording on the profile, but only a repost appears in the recommended feed. Publish the accurate update, verify that the profile provides a route to it and repeat the observation using the documented timing and account conditions. Record each surface separately. If one colleague followed the account between runs, flag the change before comparing results. If an ad uses the same content, give the media owner the correct version, date and approval. A recap can state that the profile led to the current notice and that one of two recommendation observations included it. It cannot infer an audience-wide proportion. Record which information matters to the user and who can check it. For a formal comparison of format or time, plan the study in advance and retain asset versions. A reviewer should be able to reproduce the relevant observation and understand where the conditions differ. Consider how to find a correction when an older post or quoted copy remains visible. Give people who follow that route a clear way to find the current information if the team controls the destination. In the campaign report, a stable source can answer the service question even when the recommendation result varies. Document when you next need to verify the date, how you will collect evidence and which changes would affect the original conclusion. Keep the code reference distinct so no one mistakes it for a log of actual audience delivery.

## X recommendation evidence scope

| Evidence | Supports | Verify separately |
| --- | --- | --- |
| Platform help | Surfaces, signals and settings | Cause of an individual rank |
| Public repository | Particular version and module | Individual production request and other surfaces |
| Observation | What was seen by an account at a time | Audience-wide coverage |

Record surface and date for each observation.

## Four checks before reporting

Identify the distribution question first.

- [ ] State surface and observation conditions
- [ ] Version code and documentation
- [ ] Separate observations, attribution and unknowns
- [ ] Assign an owner for the next check
